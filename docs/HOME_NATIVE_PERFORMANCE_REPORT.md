## Confirmed work and remaining root-cause uncertainty

1. Height changes during filter switches trigger Home `onLayout` even when width
   remains 353. Eleven observed layout events all reported 353→353; startup plus
   four switches produced nine Home renders. The unchanged-width state setter
   caused a redundant Home invocation. A strict width equality guard removes
   that update while retaining actual width/orientation changes. Matched trials
   reduced Home renders from two to one per switch. This is the only runtime
   optimization implemented.
2. Each filter press intentionally increments the existing recommendation seed.
   Repeated category visits can introduce new artwork paths. They are not
   necessarily warm asset visits: warm-category p95 still has three SVG cache
   misses. No batch caching, seed, rotation, ranking or output changes were made.
3. First-use cached SVG construction combines XML parsing, CSS middleware and
   React element construction. These costs remain unchanged. On cold category
   visits, production parsing plus construction p50 was 8.3ms; the separate
   all-SVG React element construction probe was 5.0ms. These overlap and **must
   not be added**. Warm p50 production parse time was zero; other old SVG mounts
   and previously unseen artwork still create elements.
4. The 432-entry runtime registry (375 artwork variants, 46 contextual icons,
   11 UI exports) is 450,787 generated bytes; SVG text is 373,270 bytes. It does
   not eagerly parse/render all assets. Local module-body evaluation was
   0.5–0.9ms before / 0.1–0.7ms after at 4× CPU. This excludes bundle decoding,
   module loading and native/Hermes startup; it is not a device startup claim.
   Thirteen production paths were parsed at Home startup, not all 432.
5. Home constructs all five eligible cards and discovery entries. The browser
   DOM median had 42 SVG roots / 204 SVG descendant elements, with 22 roots
   outside the visible content area. Native clipping and drawing of those
   offscreen trees were not measured. Mount counters prepare that investigation;
   no speculative virtualization/deferred artwork/placeholder changes were made.

The exact cause of the remaining **native Redmi visible pause is unconfirmed**.
The width update is a confirmed JS inefficiency, not proof that it dominates
Android painting. Native drawing/first paint and Expo Go overhead have no new
device measurements. The user explicitly directed local diagnostics without
waiting for a device. A temporarily started emulator/server was stopped; no
native measurements or acceptance were collected.

## Profiling prepared for Redmi

Use `EXPO_PUBLIC_GEZEK_HOME_PROFILING=1 npx expo start --clear --lan` for a local
Expo Go development session. USB is not required. Open the LAN QR on Redmi and
React Native DevTools with `j`; inspect `globalThis.__GEZEK_HOME_PROFILE__`.
The flag is off by default and remains gated by `__DEV__`. No network telemetry
or user/catalog IDs, preferences, location or SVG path values are recorded.

The bounded 200-sample snapshot provides:

- `filter_press_to_commit`: JS filter handler entry to selected content's React
  layout commit; `sequence` and `cold` distinguish trials without content IDs.
- `filter_press_to_frame_opportunity`: two subsequent animation-frame callbacks.
  A superseding press discards the stale frame sample. It is **not native paint**.
- Existing Home commits, Home/asset renders and recommendation compute samples.
- SVG cache hit/miss counts, parse+construction times and constructed JSX element
  count; production SVG mount/unmount totals. The latter do not measure drawing.

Capture each cycle before samples roll off. Counter differences describe a trial.
Reload the full JS session for cold trials; deleting only the snapshot does not
clear private asset caches or visit history. Diagnostic probes themselves add
development work, so also record flag-off screen-video timings.
